Validation Workbench — Help

For a developer or solution architect using KnowledgeForge Module 1 for the first time.

What Module 1 is for

KnowledgeForge validates whether a business-domain knowledge package is good enough that an engineering agent, given only that package, can carry out real tasks correctly. Module 1 — this Validation Workbench — is the operator's cockpit: it assembles a package, sends validation requests across the Module 2 contract to an execution Gateway (Module 3), records the evidence that comes back, derives a verdict, and lets you review and approve.

What a run proves: that, for one task against one exact snapshot of the package's knowledge, the declared checks ran and passed (or didn't), as reported by the Gateway and judged by Module 1's own rules. What it does not prove: that the package is correct in general, that untested tasks would pass, or anything about knowledge the task didn't exercise. Module 1 never invents a result and derives the verdict itself — the Gateway never supplies one.

The operator flow

register package → configure validation profile → run a task → inspect evidence → resolve review if required → approve.

  • Register a package by pointing the Workbench at its root folder (it needs a package.yaml with a durable package_id, an entry point, and a tasks directory — see workbench/PACKAGE_FORMAT.md).
  • Configure the validation profile (target environment + permitted capabilities). Until then the package is “profile not configured” and runs are blocked — Module 1 never manufactures a validation context from global defaults.
  • Run a task; the Run screen defaults to the profile. Overriding environment/capabilities is run-only and does not update the profile or qualify as current approval evidence.
  • Inspect evidence in the run screen and the package's validation history.
  • Resolve review for a needs_review run (a named human records passed/failed).
  • Approve when every active task has a latest passing, current run.

Package health, profiles, identity

Package health: the catalog shows a cheap structural status (root/manifest/entry resolvable); the package detail page assembles fully and reports discovery problems. An unhealthy package stays visible with the reason.

Durable identity: package_id is the logical package (stable across content, name, and root changes); package_fingerprint is the exact knowledge bytes a run used; the registered source/root is just where the current copy lives. History and approval hang off package_id, never the mutable source.

Validation profile: the package's canonical validation context — its target environment and permitted capability set — stored as operator configuration. It is deployment policy, not package knowledge, so it lives in Module 1's database and is excluded from every fingerprint.

Staleness and the validation context

A run's validation context is package fingerprint + task fingerprint + canonical permitted capability set + target environment. A run is stale when its execution-time context no longer equals the current one — i.e. the package knowledge changed, the task changed, or the profile's environment or capabilities changed. Capability ordering is canonicalised and never itself causes staleness. Staleness is a current comparison: a historical run is never rewritten and was not “stale at the time”; only its current qualification changes. Stale results are shown distinctly and do not count toward approval.

Outcomes and the six verdict rules

Module 1 derives the outcome from the Gateway's result using six ordered rules (first match wins). The order matters: a check that ran and failed (rule 4) is real evidence and must beat “some check didn't run” (rule 5); a technical failure (rule 2) must be caught before checks are considered; a cancellation (rule 1) wins over everything.

  1. Rule 1 — cancelled: result status cancelled → cancelled.
  2. Rule 2 — technical failure: result status failed → inconclusive.
  3. Rule 3 — no checks declared: → needs_review.
  4. Rule 4 — a declared check ran and failed: → failed.
  5. Rule 5 — a declared check did not run: → needs_review.
  6. Rule 6 — all declared checks ran and passed: → passed.

Two provenances of inconclusive: (1) Module 3 itself reported a technical failure — a valid ValidationResult with status failed (rule 2); or (2) Module 1 could not obtain or validate a usable result at all — the run ends in a Module-1 error state (below) with an effective outcome of inconclusive. Both count neither for nor against the package, and are shown distinctly.

needs_review, review, and approval

needs_review arises when Module 1 has no decisive machine evidence — a task with no declared checks (rule 3), or a declared check that did not run (rule 5). A named human resolves it to passed or failed, with the time recorded. The human resolution is stored alongside the machine verdict, never replacing it, and stays distinguishable from it. A run resolved to passed can then count as passing evidence for approval; review can never make a failed, inconclusive, or cancelled run approvable. If the validation context later changes, a resolved run becomes stale and stops counting toward current eligibility, while the resolution remains a historical fact.

How approval evidence is selected — current context first. Only runs whose validation context matches the package's current one (current package fingerprint + task fingerprint + capability set + target environment) are approval candidates. Runs under a different context — an environment/capability override, or a superseded package/task/profile — stay fully visible in history and evidence but are not candidates: they neither qualify nor disqualify current evidence. So an experiment run with an override, performed after a valid profile-matching pass, does not revoke that pass.

Among the current-context runs, newest first: inconclusive (a technical failure — the package was never really tested) and cancelled (an abandoned attempt) are skipped (neither qualify nor disqualify), so a transient Gateway outage after a successful validation does not erase an earlier pass. An unresolved needs_review blocks approval (review pending) until a human records the outcome. A resolved needs_review uses the human passed/failed. The first passed/failed is decisive — the task qualifies only if that decisive current run is passed. If a task has no run under the current context, it reads as not yet validated (never run) or re-validation required (validated before, but the context changed).

Approval is an explicit operator action (the system never approves automatically). A package is approval-eligible when every active task's current-context evidence is a decisive pass. Approval records who, when, the package fingerprint, and the active task fingerprints (plus the profile context). Changing the package, an active task, or the profile invalidates the approval's current applicability — the historical approval record is never deleted; its current validity is derived. The Module 3 outcome, Module 1's verdict, the review state, and the approval state are four separate things and are shown as such.

Evidence and artifacts

Every run preserves the ExecutionEvents, the ValidationResult (summary, check results and their output, diagnosis), and the derived verdict, all reachable from the run screen and history. Artifact names reported by Module 3 (e.g. diff.patch, test.log, transcript.log) are shown as references only — the frozen Module 2 contract does not carry artifact file contents, so Module 1 does not hold them.

Diagnosis is presented separately from raw evidence and clearly marked as an interpretation; it never determines the outcome by itself.
