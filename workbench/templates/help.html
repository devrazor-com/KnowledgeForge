Validation Workbench — Operator Guide

A complete, self-contained guide for a developer or solution architect operating KnowledgeForge Module 1 — no prior reading of the repository required. Where an authoritative specification already exists it is cross-linked (e.g. workbench/PACKAGE_FORMAT.md) rather than duplicated. Everything here describes behaviour as implemented today.

1. What the Validation Workbench is for

KnowledgeForge validates whether a business-domain knowledge package is good enough that an engineering agent, given only that package, can carry out real tasks correctly. Module 1 — this Validation Workbench — is the operator's cockpit: it assembles a package, sends validation requests across the Module 2 contract to an execution Gateway (Module 3), records the evidence that comes back, derives a verdict, and lets you review and approve. The subject under test is the package, not the model.

What a run proves: that, for one task against one exact snapshot of the package's knowledge, the declared checks ran and passed (or didn't), as reported by the Gateway and judged by Module 1's own rules. What it does not prove: that the package is correct in general, that untested tasks would pass, or anything about knowledge the task didn't exercise. Module 1 never invents a result and derives the verdict itself — the Gateway reports observable facts and never decides the outcome.

2. Quick start

  1. Point Module 1 at a Gateway with MOD3_BASE_URL, and at your accepted environment list with WORKBENCH_ENVIRONMENTS_FILE (see §16). Exact commands per OS are in the repository README.md.
  2. Start the Workbench the same way on every platform: python -m workbench.run_workbench.
  3. Open /, register a package by pasting its root folder's absolute path (§4).
  4. On the package page, configure the validation profile — target environment + permitted capabilities (§5). Until then, runs are blocked.
  5. Start a run for a task (§8) and watch it on the Run screen (§9).
  6. Inspect the result and verdict (§10); if a run is needs_review, a named human records the outcome (§10).
  7. Approve when every active task has a current passing run (§4).

3. End-to-end operator workflow

register package → open package → configure profile → select environment → select task → start run → monitor events → inspect result → read verdict & effective outcome → resolve review if required → approve. Alongside the main line: view history, cancel an in-flight run, let restart recovery reattach after a Workbench restart, Change root when a package folder moves, and activate/deactivate tasks.

The workflow legitimately stops at several points, each covered below: an unhealthy package (§4), no configured profile (§5), an unconfigured or no-longer-configured environment (§6, §16), a start rejection or transport error (§17), an operator cancellation (§13), or a needs_review verdict awaiting a human (§10). None of these are failures of Module 1 — they are states it reports faithfully.

4. Packages

Packages catalog (/). Register a package with the Package root field — an absolute filesystem path to the folder containing the package's package.yaml. On submit, Module 1 resolves the path and registers it; if you point at a path already registered (even by a different spelling — a case variant, symlink, junction or mapped drive) it simply opens the existing registration rather than creating a duplicate. A path that does not exist or is not a directory is refused with a message. Only one active registration per package_id is allowed; a second root declaring an already-registered id is refused (remove the first to move identity). The absolute path is local registration state only — it never affects any fingerprint.

Each catalog row shows a cheap, structural status — it does not assemble or fingerprint the package. The badge is one of: Unhealthy (the root/manifest/entry point cannot be resolved, with the reason), Needs profile (usable but no validation profile yet), Approval recorded (an approval exists — open the package to confirm it is still current), or No approval. remove unregisters the source; it does not delete the source files or any historical validation evidence.

Package detail (/packages/<id>). The Registered package card shows read-only, assembly-derived fields: Package id (durable logical identity), Package root, Entry point, Tasks location, Knowledge files and Tasks counts, and Package health. Health has three tiers: Healthy (assembled cleanly and tasks load), Assembled with N problem(s) (discovery reported broken links or cycles — see §18), and Unhealthy (cannot be assembled at all). An unhealthy package stays visible with its reason so you can fix it; Module 1 never invents missing content.

Change root. Use this to repoint a registration at a new folder — e.g. after moving the package or transferring it to another machine. The new root must be a valid package whose manifest declares the same package_id; Module 1 verifies this and refuses a mismatch, an already-registered path, or a physical duplicate. Only the machine-local location changes: identity, validation profile, run history, immutable snapshots and approvals are all preserved, and because the knowledge bytes are unchanged, nothing becomes stale from the move alone. (Line endings do not matter — fingerprints normalise CRLF/LF.)

Identity axes are kept separate: package_id (which logical package), package_fingerprint (the exact knowledge bytes a run used), and the registered source/root (where the current copy lives). Validation history and approval hang off package_id, never the mutable source — so unregister/re-register or a moved folder never orphans evidence.

Approval. Approval is an explicit operator action — the system never approves automatically. A package is approval-eligible only when every active task has a current, decisive passing run (see §11); the Approve button is disabled with the specific reason otherwise, and the server re-checks eligibility on submit (it never trusts the page). An approval records who, when, the package fingerprint, and the active task fingerprints plus the profile context. Changing the package, an active task, or the profile does not delete the approval — it makes the approval's current applicability derive as no-longer-current, which the card shows plainly.

5. Validation profiles

The validation profile is the package's canonical validation context: its target environment and its permitted capabilities, plus an optional recorded configurer name. It is deployment policy, not package knowledge, so it lives in Module 1's database and is excluded from every fingerprint. Until a profile is configured the package reads as “profile not configured” and runs are blocked — Module 1 never manufactures a validation context from global defaults (no profile, no run).

Configure / Reconfigure profile writes the target environment, the checked capability set, and the configurer name, and records the update time. These persisted values are what staleness and approval are judged against (§11). A run may override the environment or capabilities for that one run, but an overriding run does not update the profile and does not qualify as current approval evidence — it stays fully visible in history as an experiment.

6. Target environments

Target environments are configuration, not code. Module 3 owns and publishes the accepted logical environment names; Module 1 only presents the list you configure and sends the selected value verbatim (no mapping, normalisation, or discovery, and Module 3 need not be reachable to render the list). You configure the list in a machine-local file — see §16.

The environment selector on the profile form and the start-run form behaves as follows, so an operator can never silently submit an environment they did not choose:

  • The stored/profile environment is still configured — it is pre-selected. (No unnecessary reselection is forced.)
  • The stored environment is no longer configured — a disabled “Select an environment” placeholder is selected, and the obsolete name is not offered in the dropdown. You must pick a currently configured environment before saving or starting.
  • No profile has been configured yet — the same placeholder leads; nothing is pre-selected.
  • The environment configuration is unset or invalid — a configuration message replaces the dropdown entirely (see §16); no environment can be chosen until it is fixed.

A stored environment that is no longer configured is still shown verbatim as historical/context information (with a no longer configured marker), because historical runs and evidence that used it remain fully readable. It is simply not offered as a new choice. Removing an environment from the configured list governs future selection and new-run eligibility only — it never rewrites, invalidates, strands, or blocks recovery/cancellation of work that already exists.

7. Tasks and acceptance criteria

Tasks are JSON files, one per file, in the directory the manifest's tasks: key declares, versioned alongside the package. Each task carries an id, title, description, optional business_area/difficulty/ acceptance_criteria, and a checks list. Each task is fingerprinted over its id, description, acceptance criteria and checks — editing any of those changes the task fingerprint and therefore the validation context.

Active / inactive is operator state stored in Module 1's database, not in the task file, and it does not change a task's fingerprint. Only active tasks count toward approval. The tasks table on the package page shows each task's checks count, active state (with an activate/deactivate control), current status (§11), and fingerprint. Writing good acceptance criteria — each answerable from the package alone — and choosing whether to declare mechanical checks is authoring work; see §18.

8. Starting a run

The Start a validation run form appears once the package is healthy, a profile exists, and tasks are present; otherwise it is replaced by a message naming the specific blocker (environment configuration error, no profile, or no tasks). Controls:

  • Task — required; every task is a valid current choice.
  • Target environment — required; defaults to the profile's environment when it is still configured, otherwise forces an explicit choice (see §6).
  • Permitted capabilities — preselected from the profile; you may change them for this run.

Changing the environment or capabilities makes this run an override: run-only, it does not update the profile and will not qualify as current approval evidence. On submit, Module 1 assembles the exact snapshot, builds and validates the outbound request, creates the run, and takes you to the Run screen. If Module 1's own outbound request fails schema validation it is not sent and the run is recorded as request_invalid (§17).

A dev/mock-only panel (forced outcome and injected Gateway fault) appears only when WORKBENCH_DEV_MOCK is on. It is explicitly not part of the contract and is hidden in production.

9. Monitoring a run and events

The Run screen streams progress live (server-sent events) and lays the run out as eight stages: Inputs, Module 1 Assembly (package id, execution-time package fingerprint, task fingerprint, and whether this run's context is current or stale), ValidationRequest (with Module 1's outbound validation result and the raw JSON), Module 2 Contract (the start operation), Gateway, ExecutionEvents, ValidationResult, and Module 1 Verdict. Module 1 validates every ExecutionEvent against the contract on receipt and checks the sequence; a gap, duplicate, out-of-order or schema-invalid event ends the run as protocol_error rather than being silently accepted.

The run state badge moves through submitting → running → terminal (a ValidationResult and verdict exist) or error (a Module-1 error state, effective outcome inconclusive). Two banners may appear: an ephemeral recovery note (restart reattachment, §14) and a durable cancellation-delivery note (§13). When a run ends in error, the downstream stages read “not reached” rather than sitting blank — Module 1 never fabricates a result to fill them.

10. Results, verdicts and effective outcomes

The ValidationResult (shown when the run is terminal) reports the Gateway's status and summary, per-check results (id, passed/failed, exit code, and any output), any artifact names, and an optional diagnosis. Artifact names (e.g. diff.patch, test.log) are shown as references only — the frozen Module 2 contract does not carry artifact file contents, so Module 1 does not hold them. The diagnosis is Module 3's interpretation, shown separately and marked advisory; it never determines the outcome by itself.

Module 1 derives the verdict from the Gateway's result using six ordered rules, first match wins. The order matters: a cancellation (rule 1) wins over everything; a technical failure (rule 2) is caught before checks are considered; a check that ran and failed (rule 4) is real evidence and beats “some check didn't run” (rule 5).

  1. Rule 1 — cancelled: result status cancelled → cancelled.
  2. Rule 2 — technical failure: result status failed → inconclusive.
  3. Rule 3 — no checks declared: → needs_review.
  4. Rule 4 — a declared check ran and failed: → failed.
  5. Rule 5 — a declared check did not run: → needs_review.
  6. Rule 6 — all declared checks ran and passed: → passed.

Two provenances of inconclusive: (1) Module 3 itself reported a technical failure — a valid ValidationResult with status failed (rule 2); or (2) Module 1 could not obtain or validate a usable result at all — the run ends in a Module-1 error state (§17) with an effective outcome of inconclusive. Both count neither for nor against the package, and are shown distinctly.

Effective outcome is what history and approval use. Its source is one of: machine (Module 1's own verdict), review (a human resolved a needs_review), or error (an error run → inconclusive). A human resolution is stored alongside the machine verdict, never in place of it, and stays distinguishable.

Human review

needs_review arises when Module 1 has no decisive machine evidence — a task with no declared checks (rule 3), or a declared check that did not run (rule 5). A named human resolves it to passed or failed, with the time recorded. A run resolved to passed can then count as passing evidence for approval; review can never make a failed, inconclusive, or cancelled run approvable. If the validation context later changes, a resolved run becomes stale and stops counting toward current eligibility, while the resolution remains a historical fact.

11. Current versus stale evidence

A run's validation context is package fingerprint + task fingerprint + canonical permitted capability set + target environment. A run is current when its execution-time context equals the package's current one, and stale when it no longer does — i.e. the package knowledge changed, the task changed, or the profile's environment or capabilities changed. Capability ordering is canonicalised and never itself causes staleness.

Staleness is a current comparison, not a rewrite: a historical run was never “stale at the time” and its evidence is never altered — only its current qualification changes. Stale results, including runs made with an environment/capability override, remain fully visible but do not count toward approval. Approval considers only runs whose context matches the current one; among those, newest-first, inconclusive/cancelled are skipped, an unresolved needs_review blocks, and the first passed/failed decides. A task with no run under the current context reads as not yet validated (never run) or re-validation required (validated before, but the context changed).

12. Fingerprints and evidence

The package (knowledge) fingerprint is a hash over the assembled sequence of (package-relative path, newline-normalised content). It is machine-independent: the same knowledge produces the same value on any OS and under any absolute root, and the manifest and root path are excluded. The task fingerprint is separate, and the validation-context identity combines package fingerprint, task fingerprint, capabilities and environment (§11). Full specification: workbench/PACKAGE_FORMAT.md.

Every run preserves the ExecutionEvents, the ValidationResult, and the derived verdict as immutable evidence, reachable from the Run screen and history. The Run screen also shows a factual comparison of the run's execution-time snapshot fingerprint against what the currently-registered package assembles to now — so you can see at a glance whether the package has changed since the run.

13. Cancellation

Cancelling asks the Gateway to stop the run. Operator intent is recorded immediately and is separate from what Module 1 knows about delivering that request. Module 1 sends exactly one physical cancel per click — a repeated cancel is contractually undefined, and a transient server error does not establish whether the first was acted on — so it never auto-retries. You can click Cancel again while the run is still non-terminal; a failed or rejected attempt never hides or disables the control.

acknowledged does not mean the run is cancelled (acknowledged ≠ cancelled) — it means Module 3 acknowledged receiving the request. The run is only cancelled when the contract cancelled event/result arrives and verdict rule #1 applies. acknowledged is sticky: a later failed retry cannot downgrade the durable fact that an earlier request was acknowledged, though the immediate response still tells you what the latest attempt did.

14. Recovery and reattachment

If the Workbench restarts while runs are in flight, it reconciles them automatically at startup. Recovery observes existing runs by their run_id; it never re-issues start and never re-issues cancel. Cases, as implemented today:

  • Interrupted around start (acceptance unknown) → recorded start_unresolved: Module 1 cannot tell whether Module 3 created a run, so it will not retry (§17).
  • A terminal event was persisted but the result wasn't retrieved → recovery completes the retrieval.
  • The run deadline expired while the Workbench was down → recorded timed_out.
  • Accepted and still in progress (including a run whose cancellation was already requested) → recovery resumes observing, tolerating a transient unreachable Gateway within the original run deadline and showing an ephemeral “recovering” note. A previously requested cancellation is not reissued — its recorded delivery state stands, and you decide whether to Cancel again.

The “recovering” note is ephemeral process state, not durable evidence: it clears once the Gateway is reachable again, and is reconstructed by the next reconciliation if the Workbench restarts again.

15. History and historical readability

A package's validation history is keyed by durable package_id and spans every content version the package has had. Each row is immutable evidence tied to the exact snapshot that run used: run id, task, outcome (verdict + rule, or error kind → inconclusive, or a non-terminal state), run state, environment and capabilities, the snapshot fingerprint, and start time. A cancellation-delivery note appears where relevant.

Historical readability is preserved unconditionally. Changing the package, editing the profile, or removing an environment from the configured list never rewrites, hides, or invalidates existing runs — a run that used a now-removed environment still displays that environment and its recorded outcome. The current/stale badge in history is a current comparison against today's profile (§11); it changes what currently qualifies, never the recorded facts.

16. Configuration and fail-closed states

MOD3_BASE_URL points Module 1 at a Module 3 Gateway (default is the dev mock). WORKBENCH_ENVIRONMENTS_FILE points at a machine-local UTF-8 text file listing the accepted Module 3 environment names, one per line; blank lines and full-line # comments are ignored, surrounding whitespace is trimmed, a byte-order mark and either line ending are tolerated, and a duplicate name is a configuration error. The file is reread on demand, so edits take effect without a restart. Names are used exactly as written — no case-folding or aliasing. The recommended convention is workbench/local/environments.txt (git-ignored, kept separate from the disposable workbench/data/). Copy workbench/environments.example.txt to start.

Fail-closed, with no synthetic fallback. When the environment configuration is missing or invalid, Module 1 shows an actionable message instead of an environment dropdown and blocks new runs, in one of four states: unset (the variable isn't set), unreadable (the file can't be read), empty (no names after ignoring blanks/comments), and duplicate (a name appears twice — the message cites the physical file line numbers). Fixing the file and reloading clears the state. Configuration never rewrites or strands existing work — it governs future selection and new-run eligibility only.

17. Errors and troubleshooting

When no valid ValidationResult is obtained, the run reaches a terminal Module-1 error state (effective outcome inconclusive) with a Module-1-authored error kind:

{{ name }}{{ desc }}

Each error and unusual state below is described as: What happened? → What does Module 1 know? → What should I do? → What should I not assume? The last line matters most — an ambiguous state must not be read as more certain than the evidence permits.

gateway_unreachable

What happened?
Module 1 could not reach Module 3 over the network (at start, or mid-run).
Module 1 knows
The network call failed. If it failed at start, no run was created on the Gateway.
Do
Check MOD3_BASE_URL, the Gateway, and the network path, then start a fresh run.
Don't assume
That the package failed validation — nothing was tested. This is inconclusive.

start_rejected

What happened?
Module 3 declined the ValidationRequest at start; the Gateway's reason is shown verbatim.
Module 1 knows
No run was created on the Gateway. The rejection is the Gateway's decision, recorded as-is.
Do
Read the reason, correct the request/package/environment it points to, and start a fresh run.
Don't assume
That the package is bad — a rejected start says nothing about the knowledge's quality.

gateway_http_error

What happened?
Module 3 returned a persistent HTTP error (e.g. a 5xx). A transient 5xx is retried a small fixed number of times within the run deadline before this is recorded.
Module 1 knows
The Gateway responded, but not with something usable, and retries did not clear it.
Do
Check Gateway health/logs; once it is healthy, start a fresh run.
Don't assume
A verdict about the package. This is a transport/server condition, not test evidence.

protocol_error

What happened?
Module 3 sent something that broke the contract — malformed JSON, a schema-invalid event/result, or a sequence anomaly (gap, duplicate, out-of-order).
Module 1 knows
It stopped at the first violation rather than accepting suspect data. The recorded payload shows what was received.
Do
Share the recorded payload with the Gateway owner; start a fresh run once resolved.
Don't assume
Any partial events “counted”. An interrupted, contract-violating stream is inconclusive.

request_invalid

What happened?
Module 1's own outbound ValidationRequest failed schema validation, so it was not sent.
Module 1 knows
Nothing left Module 1; Module 3 was never contacted. The validation errors are recorded.
Do
This usually indicates a package/task data issue surfaced during assembly — fix it and retry. If it persists with valid inputs, report it (it may be a Module 1 defect).
Don't assume
That the Gateway rejected anything — it never saw the request.

timed_out

What happened?
Module 1's authoritative run deadline (the Gateway's execution budget plus a small guard) expired before completion. Module 1 recorded the timeout and sent a best-effort cleanup cancellation.
Module 1 knows
A run exists on the Gateway; Module 1 simply stopped waiting. It did not receive a result.
Do
Investigate why the task ran long; start a fresh run if you still need the result.
Don't assume
That the remote work stopped. A timeout is Module 1 ceasing to wait, not proof the Gateway halted.

start_unresolved

What happened?
The Workbench was interrupted around start; on recovery it cannot tell whether Module 3 accepted the start request.
Module 1 knows
A local attempt exists; whether a remote run was created is genuinely unknown. Module 1 will not retry, because retrying could create duplicate execution.
Do
Start a fresh validation run — it gets a new run_id and is a new attempt, not a retry of this one.
Don't assume
That the original attempt did nothing. Because the contract provides no idempotent start or lookup, an orphaned execution may still be running until the Gateway reclaims it; marking this attempt terminal resolves Module 1's ambiguity, not the remote work.

Cancellation-delivery states (unknown / undelivered / rejected / acknowledged)

What happened?
You requested a cancellation; the state describes what Module 1 learned about delivering it — see §13.
Module 1 knows
Only the delivery outcome. Even acknowledged means the request was received, not that the run stopped.
Do
For undelivered/rejected/unknown, you may Cancel again while the run is non-terminal. For acknowledged, wait for the Gateway's cancelled result.
Don't assume
That the run is cancelled until the contract cancelled event/result arrives and rule #1 applies.

Environment configuration failures (unset / unreadable / empty / duplicate)

What happened?
The environment configuration is missing or invalid; the selector is replaced by a message and new runs are blocked (fail-closed) — see §16.
Module 1 knows
Exactly which of the four conditions applies; for a duplicate, the physical file line numbers.
Do
Fix WORKBENCH_ENVIRONMENTS_FILE (set it, make it readable, add names, or remove the duplicate) and reload — no restart needed.
Don't assume
That existing runs are affected. Configuration governs future selection only; history is untouched.

Environment no longer configured

What happened?
A profile's stored environment is not in the current configured list.
Module 1 knows
The stored value verbatim (shown as context) and that it is no longer offered as a choice.
Do
Select a currently configured environment for the next run, or reconfigure the profile.
Don't assume
That historical runs using it are invalid — they remain fully readable and unchanged.

Unhealthy package / discovery problems (missing / cycle / outside_root)

What happened?
Unhealthy: the root/manifest/entry point could not be resolved at all. Assembled with problems: assembly succeeded but discovery reported a broken link (missing), a circular reference (cycle), or a link outside the package root (outside_root).
Module 1 knows
The specific fault and where; it kept the registration visible and did not invent content or silently skip anything.
Do
Fix the package (see §18) and reload. A reported problem is a real problem to correct, not a warning to tolerate.
Don't assume
That a partially-assembled package is complete — problems mean some intended knowledge may be absent from the snapshot.

Task status: not_validated vs revalidation_required

What happened?
not_validated: the task has no runs at all under any context. revalidation_required: it has runs, but none under the current validation context.
Module 1 knows
Whether any current-context evidence exists. Prior evidence still exists in history; it just no longer qualifies.
Do
Start a run under the current context to produce qualifying evidence.
Don't assume
That revalidation_required means a past failure — the context simply changed.

needs_review

What happened?
The run completed but Module 1 has no decisive machine evidence — no checks were declared (rule 3) or a declared check did not run (rule 5).
Module 1 knows
Exactly which rule applied. It cannot mechanically decide pass/fail, and it will not guess.
Do
A named human records passed/failed; the resolution is kept distinct from the machine verdict.
Don't assume
That it is a pass or a fail on its own — it is an explicit request for human judgement.

Current vs stale evidence

What happened?
A run's validation context no longer equals the package's current one (§11).
Module 1 knows
The exact contexts it is comparing; the run's evidence is unchanged.
Do
Re-validate under the current context if you need qualifying evidence.
Don't assume
That a stale run was wrong or has been rewritten — only its current qualification changed.

18. Package-authoring best practices

This section helps you prepare packages the Workbench can validate. Each statement is labelled Workbench-enforced (the implementation requires it), Current limitation (a known present-day constraint, not a promise of future change), or Recommended practice (authoring judgement). The authoritative format specification is workbench/PACKAGE_FORMAT.md; this is orientation, not a second spec.

  • Workbench-enforced A package is a root folder with a package.yaml declaring a required package_id (lowercase letters, digits, single hyphens — no spaces), entry_point, and tasks directory. The manifest is structural config: it is excluded from assembled knowledge, never crosses Module 2, and never enters any fingerprint.
  • Workbench-enforced From the entry point, knowledge is discovered via front-matter dependencies and relative Markdown links, followed recursively. The assembled order is entry-first then the rest sorted, so resolution does not depend on link/file order — a reference to a file that sorts later resolves normally, and is not a problem in itself.
  • Workbench-enforced Discovery problems are reported, never invented or silently skipped. Treat each as a correction to make, not a tolerable warning:
    • missing — a referenced .md file was not found. Fix the link target or add the file.
    • cycle — files reference each other in a loop. Restructure so the dependency graph is acyclic.
    • outside_root — a link resolves outside the package root, and is refused. If the material is genuinely part of the package, bring it inside the root and reference it consistently within the package boundary; if it is not, remove the link. Do not normalise an external reference as an ignorable warning.
  • Recommended practice Write acceptance criteria that are answerable from the package alone; prefer a small number of well-shaped tasks over many thin ones.
  • Recommended practice An honest checks: [] (no mechanical verification) is preferable to a meaningless check. It yields needs_review (rule 3), which correctly asks for human judgement rather than manufacturing a machine pass.
  • Recommended practice Remember that editing package content changes the package fingerprint and editing a task changes its fingerprint — either makes prior approval evidence no-longer-current, requiring re-validation (§11). Plan edits with that in mind.
  • Current limitation Relative Markdown links are matched literally: a link written with a percent-encoded space (%20) is looked up as a literal %20 filename and reported missing. Prefer paths and folder names without spaces today. This is a current limitation, not a documented future behaviour, and is not changed here.
  • Current limitation The ADLC/front-matter handling has a known unresolved issue; it is described as a current limitation only and is not addressed by this guide.

19. Operator best practices

  • Configure the validation profile before running — Module 1 will not manufacture a context, and runs are blocked until you do.
  • Read inconclusive and needs_review honestly: neither counts for or against the package. Do not treat an inconclusive run as a failure or a pass.
  • Never infer that remote work stopped from start_unresolved or timed_out; start a fresh run rather than assuming.
  • Use environment/capability overrides deliberately — they are experiments that never qualify as current approval evidence.
  • After editing a package or task, re-validate the affected tasks before relying on approval; a moved folder (Change root) alone does not require re-validation.
  • Approval is explicit and yours to give — confirm the package shows Approved · current, not merely “Approval recorded”, before treating a package as approved.

See also workbench/PACKAGE_FORMAT.md (package format), workbench/REQUIREMENTS_CLARIFICATIONS.md (settled interpretations, open Gateway-owner questions, and recorded operator-experience findings), and the repository README.md (install and launch).
